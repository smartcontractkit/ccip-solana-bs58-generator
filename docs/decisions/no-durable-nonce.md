# Why the output carries no durable nonce

The CLI compiles a message against a recent blockhash and never uses a durable nonce. Nothing this
tool emits is ever signed, so there is no signature for a nonce to keep alive.

## What a durable nonce is for

A durable nonce removes transaction expiry for something **signed now and submitted later**:
offline and air-gapped signing, scheduled transactions, and multisig propose-then-execute patterns.
The signature commits to the blockhash, and the blockhash is what expires - 150 blocks, roughly
60-90 seconds.

Those are real use cases, and this CLI is not one of them. Its only signing path, `--execute`, signs
and sends immediately; see [EOA execution](../concepts/eoa-execution.md).

## Why it buys nothing here

This tool emits a serialized **message**, not a transaction. It has no signatures.

Squads stores that message in the `VaultTransaction` account under a `message` field whose struct is
`numSigners`, `numWritableSigners`, `numWritableNonSigners`, `accountKeys`, `instructions`,
`addressTableLookups`. No blockhash field and no signature field, so nothing in the stored message
can expire. The blockhash the CLI compiles against is real - `@solana/web3.js` requires it to
compile a message, and the pre-flight simulation needs it valid - but it has no life after import.

Every transaction that *is* signed fetches its own blockhash at send time:

| Step | Signed by | Blockhash |
| --- | --- | --- |
| import (`vaultTransactionCreate` + `proposalCreate`) | the importer | fresh at import |
| each `proposalApprove` | one member, separately | fresh at each vote |
| `vaultTransactionExecute` | the executor | fresh at execution |

Approvals are on-chain state, not accumulated signatures: `Proposal.approved` is a `Vec<Pubkey>` of
member keys. No signature has to survive longer than its own submission, and a proposal can sit
pending indefinitely - `ProposalStatus` has no `Expired` variant, and `time_lock` is a minimum delay
rather than a deadline.

Verified on devnet: a `set-rate-limit-admin` transaction generated by this CLI, imported to a
3-member threshold-2 multisig, approved 16 minutes apart and executed 4 minutes after that - 20m27s
from import to execution, four transactions carrying four different blockhashes, the stored message
byte-identical across 23 reads spanning the whole window.

## Why adding one would be wrong

An `advanceNonceAccount` instruction inside the generated instruction list would not act as a nonce.
The runtime recognises a durable-nonce transaction only by inspecting instruction 0 of the
**top-level** transaction and matching the nonce account's stored value against the message's
`recent_blockhash` field. Instructions stored in a `VaultTransaction` are neither: they are CPI'd
from `vaultTransactionExecute`, and the stored message has no blockhash field to hold a nonce.

It would not be rejected as malformed. It would execute as an ordinary System Program call and
advance the nonce for real, invalidating any outstanding transaction signed against the old value.

## What does have a clock

One instruction: `create-lookup-table`. Its address derives from a recent slot, which the ALT
program checks against the `SlotHashes` sysvar - 512 slots, about 3.5 minutes. That is slot
derivation, not blockhash expiry. Prefer `pnpm create-alt` (EOA-paid, Squads vault as authority).
See [PDA derivation](../concepts/pda-derivation.md).

## What does end a pending proposal

A Squads config change, not elapsed time. See
[the gotcha](../gotchas/index.md#config-change-invalidates-pending-proposals).
